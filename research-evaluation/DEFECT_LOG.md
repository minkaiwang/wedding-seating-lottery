# Evaluation Defect Log

| ID | Baseline status | Trigger | Observed consequence | Resolution | Regression evidence |
|---|---|---|---|---|---|
| EC-001 | Reproduced at `e63c8d1` | Synchronize a stable-ID row after an Excel-origin row containing `uid` and the same name/table/tag fields | The documented legacy upgrade key could not match; the person could be recreated instead of retaining lottery-side identity and state | Use a dedicated public-field legacy identity key that intentionally ignores Excel `uid` only during stable-ID upgrade | `WeddingSeatingLegacyBaseline.test.ts` |
| EC-002 | Reproduced from baseline merge behavior | Deliver the same stable-ID row more than once in one synchronization payload | Duplicate lottery people were created for one planner guest | Deduplicate accepted rows by protocol identity with deterministic last-row-wins semantics | `WeddingSeatingMerge.test.ts` |
| EC-003 | Reproduced by the live-sync E2E fault pilot | Allow the initial READY push and timed retries to persist overlapping roster snapshots | In-memory merges completed, but unordered IndexedDB clear/add operations could leave the persisted roster empty | Serialize immutable snapshots and replace both person stores atomically; emit completion only after persistence resolves | `run-live-sync-faults.mjs` |
| EC-004 | Reproduced from baseline legacy-upgrade behavior | Upgrade two legacy rows with the same name/table/tag fields but different `uid` values to two stable planner IDs | The single-value legacy map could reuse one lottery object for both rows, duplicating an internal ID and dropping the other person | Store an ordered candidate list per public identity and consume each legacy person at most once | `WeddingSeatingMerge.test.ts` (`consumes separate legacy rows...`) |
| EC-005 | Reproduced from baseline exclusion lookup | Delete an Excel-origin row, then receive the same row with a stable planner ID | The historical `uid` exclusion key was not considered once the stable ID became primary, so the deleted row could return | Match exclusions against stable, structured fallback, and historical `uid` key candidates | `WeddingSeatingMerge.test.ts` (`honors an old uid-based exclusion...`) |
| EC-006 | Reproduced from delimiter-based fallback keys | Use public identity fields containing the `|` delimiter or canonically equivalent Unicode/outer whitespace | Distinct fallback identities could collide, while equivalent identities could fail to match | Use structured fallback keys and normalize scalar text to trimmed NFC form; retain historical keys only as exclusion candidates | `WeddingSeatingMerge.test.ts` and `WeddingSeatingProtocol.test.ts` |
| EC-007 | Reproduced during the post-publication audit of `b4381ac` | Reject persistence after accepting sequence N, then retry the same sequence N | The retry could be rejected as stale even though sequence N had not reached durable storage | Track accepted and persisted sequence watermarks separately; roll back the accepted watermark after an unsuperseded persistence failure | `WeddingSeatingProtocol.test.ts` and `WeddingSeatingLiveSync.test.ts` |
| EC-008 | Reproduced from the baseline one-click bridge | Send a READY or DONE message from a different window on the configured lottery origin, or send DONE before the import snapshot | The planner could send data to, or report completion from, a message peer other than the popup opened for the current handoff | Bind both handshake directions to the opened `WindowProxy` and accept DONE only after the import snapshot has been sent | `lotteryBridge.test.ts` |

Only reproducible implementation defects belong in this table. Environment setup failures, harness incidents, and expected safeguard rejections remain in the raw audit trail. Earlier browser batches are retained for provenance and are excluded from the current JSS estimates unless explicitly named.
